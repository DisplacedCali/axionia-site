# Review — 2026-09-21

A pass over the research pipeline and the admin surfaces around it, prompted
by the Vida Health run stalling twice in one evening. Two of the findings
below are the direct cause of that evening; the rest surfaced on the way.

Ordered by what it costs to leave alone. Nothing here is built except where
it says shipped.

Read `PROJECT_STATE.md` first for where things stand.

---

## 1. Resume on a finished job mints a duplicate report — SHIPPED? yes, 2026-09-22

`attachResearchToReport()` has no idempotency guard. It calls
`promoteRunToReport()`, which unconditionally `insert`s a new `public.reports`
row and a new `public.report_requests` row. Calling it twice for one run
produces two reports.

The client calls it automatically. `drive()` in `ResearchPanel` fires it on
any `advanceResearch` response carrying `done && runId`:

```js
if (r.done && r.runId) {
  const attached = await attachResearchToReport({ requestId, runId: r.runId, ... });
```

And `advanceJob()` returns exactly that shape for a job that is *already*
finished — the `!claimed` branch returns `done: current.status === "complete"`
with `runId: current.runId`. So **clicking Resume on a completed job creates a
second report of the same research**, versioned v2, then v3, one per click.
Nothing warns, because from the panel's point of view it just succeeded.

*Fix:* `attachResearchToReport` should look for an existing report with this
`research_run_id` and return it rather than promoting again. The column
already exists and is already written on the row.

*What would change our mind:* nothing — re-promoting the same run is never
the intent. The only question is whether the guard lives in the action or as
a unique index on `reports.research_run_id`, and it should probably be both.

## 2. Every admin-initiated run orphans a queue row — SHIPPED? mitigated, 2026-09-22

`research.promote_research_to_report()` inserts its own `report_requests` row,
commented "Queue row, so this appears in the admin UI alongside inbound work."
That was right when the pipeline was driven from outside the site. It isn't
now: `attachResearchToReport` immediately repoints the report at the request
the analyst actually started from —

```js
.update({ request_id: args.requestId, research_run_id: args.runId, ... })
```

— leaving the row the function just created sitting in the queue at
`status = 'in_review'`, `origin = 'admin'`, with no report attached to it and
no way to tell from the list that it is a shell. One per admin-initiated run,
forever, inflating every open-work count on `/admin`.

*Fix:* the function should take the request id as an argument and skip the
insert when one is supplied. Both callers know it.

## 3. A failed step reports a canned string and discards the real one — SHIPPED? yes, 2026-09-22

This is what cost most of the evening. When a required step fails, the panel
does:

```js
if (r.status === "failed") {
  setErr("A required step failed. Fix the cause and run again — completed waves are kept.");
```

`r.error` — the actual message, already on the response — is thrown away and
replaced with a sentence that names no step and no cause. The real string
("Workforce segmentation returned no usable segments after retry.") was
sitting in `pipeline_jobs.last_error` the whole time and could only be read
by opening the SQL editor.

*Fix:* render `r.error` when it is present and keep the canned sentence as
the fallback for when it isn't.

## 4. Per-step errors never leave the server — SHIPPED? yes, 2026-09-22

The runner stores a message on each failed step (`steps[id].error`), and the
step list sent to the client drops it:

```js
steps: STEPS.map((s) => ({ id, label, status, degraded, ms }))   // no error
```

So the red ✕ next to "Workforce" can never explain itself, even though the
explanation is two fields away. Adding `error` to that map costs nothing and
puts the cause next to the step that produced it, which is where someone
debugging is already looking.

## 5. A refused claim polls for 75 seconds and then lies — SHIPPED? yes, 2026-09-22

`claimJob` declines to re-claim a `'running'` job until it is 10 minutes
stale. When it declines, `advanceJob` returns `wave: null`, which
`advanceResearch` turns into `retryAfterMs: 3000`, and `drive()` loops up to
25 times — 75 seconds of polling a job nobody is advancing — before reporting
"Stopped after 25 waves without completing," which is not what happened. No
wave ran at all.

*Fix:* the `!claimed` path is distinguishable (`wave === null` and not done)
and should return a status the panel can render honestly — "this job is held
by another run, or was left mid-wave; it can be picked up in N minutes."

## 6. The vendor-evidence engine has no way in — SHIPPED? no

`lib/modules/vendor-evidence/` is complete: schema (038), three-call pipeline,
and `POST /api/modules/vendor-evidence/from-file`, whose first parameter is
documented as "report_files.id — the already-uploaded vendor deck to run
against." It was built to be called from a button on a file row. That button
does not exist, so the only Run control anywhere near an uploaded vendor PDF
is the one that starts the *employer* research pipeline.

That is how Vida Health — a vendor, whose own decks this module was written
from — ended up as an employer research request. Not a misuse; the only door.

*Fix:* a "Run evidence analysis" action on each PDF row in the files panel,
posting `fileId` + `vendorName` to the route that already works, and somewhere
for the result to land.

## 7. Two keys for one company — SHIPPED? no

`research.companies` is unique on `lower(name)`; `public.companies` is unique
on `domain`, and `promote_research_to_report` resolves the public row by
domain with a placeholder fallback. Two spellings of one employer produce two
research rows; two domain resolutions produce two public rows, and the version
chain — which reads `where company_id = ...` — then starts over at v1 for what
is really the same company.

Worth confirming against the duplicate `v1 · Vida Health` pair currently on
that company's hub before acting, since finding 1 also produces duplicates by
a different route and the two are hard to tell apart after the fact.

## 8. Housekeeping — SHIPPED? yes

Five `.dryrun-build-old*/` directories (1.4MB) and three `dryrun_out*.txt`
files were sitting untracked. Root cause: `scripts/dryrun-research.js` opens
with `fs.rmSync(OUT, ...)`, which fails inside the agent sandbox — it cannot
unlink under the mounted repo — so sessions worked around it by renaming the
old build aside. Deleted, and `.gitignore` now globs `.dryrun-build*` and
`dryrun_out*.txt` so the workaround stops leaving evidence.

`CLAUDE.md` documented `git status --porcelain --no-optional-locks`. The flag
is a pre-command option; written after the subcommand it exits 129 with
`unknown option`, which reads as a clean tree if stderr is being swallowed.
Corrected in the same pass.

## 9. The migrations line in PROJECT_STATE is stale again — SHIPPED? partly

It read "002–033" while the directory held through 038; corrected to 039, and
040 landed in the same working tree. A line that has been wrong three times is
a line that wants deleting rather than maintaining — the health endpoint
already reports which migrations are missing, and it cannot go stale.

## The pattern worth naming

Findings 3, 4 and 5 are one fault wearing three hats: **the system knows why
it failed and does not say so.** The message exists, in the response or in
Postgres, and something between there and the screen replaces it with a
generic sentence or drops it. An evening went into recovering, by reading
source and running SQL by hand, information the software already had.

That is worth more than the individual fixes. Anywhere a failure is caught,
the caught message should reach the person, and the generic line should be
the fallback rather than the default.

# Addendum — 2026-09-22

## 10. Promotion depended on the browser, and that is what was losing reports

The finding the rest of this file was circling. `attachResearchToReport` had
exactly one caller: `ResearchPanel`. Nothing server-side ever turned a
completed run into a report.

So the pipeline was durable — one wave at a time, resumable, survives a closed
tab — right up until the last step, which needed a live tab to fire a second
action. And the page is at its least responsive at precisely that moment: Next
serialises server actions, the run has just made a dozen of them, and the
refresh that makes the page usable again aborts the promotion in flight.

The evidence, from one request: **five jobs, four reaching `complete` with a
`run_id`, four rows in `research_runs`, and two reports.** Every run was saved.
Half of them were never promoted, and nothing would ever promote them, because
the only code that could had been unmounted.

*Fixed:* `finish()` promotes server-side as the last act of a run, through a
new `promoteRunForRequest()` that is idempotent on (run, request). Its own
try/catch, and deliberately not allowed to fail the job — by then the research
is saved, so a promotion failure costs a retry, not the work. The panel still
calls the same helper, which now finds the report already there and returns it;
that path stays for cached runs and for runs predating this change.

*What would change our mind:* nothing about the direction. The open question is
whether the panel should call it at all any more, or just read what the runner
produced — worth revisiting once there is a second consumer of a completed run.

## 11. Still open after today

- **The freeze itself.** Server-side promotion makes it non-fatal — a frozen or
  refreshed page can no longer cost a report — but the page still stops
  responding while a run finishes, and that is diagnosed from the code rather
  than observed. Finding 5's fix removes up to 75 seconds of pointless server
  actions from that window, which is a contributor and probably not all of it.
  Needs a browser with the network panel open, not more source reading.
- **Orphaned runs from before this change** are still unpromoted. They are
  findable: a `research_runs` row with no `reports` row carrying its id.
- **Finding 2 is mitigated, not fixed.** The phantom queue row is now archived
  immediately instead of sitting in the open counts, but the plpgsql function
  still creates it. Fixing it properly means a migration that lets the caller
  pass the request id in.


## 12. Production was running a function this repo does not define

The root cause under everything above, found 2026-09-22 after two days of
fixing things downstream of it.

Production carried `promote_research_to_report(p_run_id uuid, p_user_id uuid,
p_title text)`. Every caller passes `(run_id, domain, title)`. The repo's
version — second parameter `p_domain text` — is created inside conditional
`DO` blocks in `research_schema.sql` that skip silently and only `raise
notice` when `report_requests`, `origin` or `reports.user_id` aren't in the
expected state, so on the run that mattered it was skipped and the
axionia-app-era version stayed.

It did not fail loudly. It promoted fine — nineteen reports, all with
content, all correct. It simply never anchored them to a company, so
`company_id` came back null on every one, and every company-scoped query on
the site was blind to reports that existed and were right. Paired with the
`maybeSingle()` fault in finding 13, the product reported "no research
attached" while holding eight complete reports for that one request.

*Fixed:* migration 041 drops the stale overload and installs the repo's
definition. Dropped rather than left alongside, because with both present a
call of `(uuid, null, null)` is ambiguous between `(uuid, uuid, text)` and
`(uuid, text, text)` and Postgres refuses it — which would turn a silent
wrong answer into a hard failure on every run.

*The lesson worth keeping:* a schema file whose creation steps can be skipped
by a conditional, reporting success via `raise notice`, will eventually be
skipped, and nothing downstream will say so. The health endpoint reports
missing migrations; it does not report a function whose signature drifted.
That gap is what cost two days.

## 13. maybeSingle() on a non-unique key blinded the request page

`request_id` is not unique on `reports` — `app/admin/actions.ts` writes a
titled shell with no content, `promote_research_to_report` writes the real
one, and both point at the same request. PostgREST's `maybeSingle()` errors
on more than one row and hands back null, so the page concluded there was no
report at all and offered to run research again. Each run added another row,
which made the collision more certain. Five jobs against one request is what
that loop looks like from the outside.

The same pattern in `actions.ts` meant its own "does a report already exist?"
check also came back empty once there were two, so it inserted another shell
each time.

*Fixed:* both reads now take the newest row and prefer one carrying research,
so an empty shell can never mask a real report.
